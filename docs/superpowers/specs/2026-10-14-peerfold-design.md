# Peerfold 设计文档

- 日期：2026-10-14

## 一、这是什么，为什么做

peerfold 把 N 台机器（Windows / Linux）上的文件，聚合成**一台机器上的一个本地目录树**。你在自己的主机器上打开一个普通目录，里面每一台机器是它的一个子目录；你像用本地文件一样浏览、打开、修改它们，改动落回文件真正所在的那台机器。

运行形态效仿 NGINX：一个常驻进程 + 一份配置文件 + 无 GUI。

**为什么选"挂载 + 懒加载"而不是同步盘。** 同步盘要求先把文件搬过来才能用，磁盘和等待都是成本，而且它在你的机器上多存了一份真相。peerfold 不复制真相——列表是活的、借来的；内容是你要用的时候才拉的，改完就还回原主。观察者本地几乎不占空间。

**什么算成功。** 在开了聚合开关的那台机器上：`ls` 立刻列出所有其他机器的文件；`cat` 一个远端文件能出内容；用编辑器改完保存，去那台机器上 `cat` 同一个文件，内容真的变了。

## 二、术语

| 词 | 含义 |
|---|---|
| **server** | 中枢。所有 client 出站拨号连它。持有唯一的全局元数据索引。自己不挂载，不出现在任何树里。 |
| **client** | 跑在每台被聚合的机器上的进程。默认身份是供货方：出让配置里指定的那些目录。 |
| **aggregate 开关** | client 配置里的一项。开了才参与聚合；全局只允许一台为 on。 |
| **观察者** | 开着 aggregate 开关的那台 client。既供货，又是唯一能看到整棵树的那台。 |
| **树** | 观察者本地的挂载点，形如 `/mnt/peerfold/<client名>/...` |

## 三、已确定的形态（对话中你定的）

1. **星形拓扑**：client 之间永不互连，一切只经 server。好处是 client 在 NAT 后面也无所谓、鉴权只有一处、观察者的视图只认识 server 一个端点。代价是 server 是数据中转站、带宽是硬成本，server 挂了全盘不可用；另外因为 client 之间不握手，端到端加密不是白来的。

2. **聚合即虚拟挂载 + 懒加载**：
   - **列表**：server 的全局索引直接给观察者，实时，一次都不回源 client。
   - **读**：只有真的去打开某个文件，才向归属 client 拉字节。
   - **写**：保存后字节回 server，落到原 client 的磁盘上。

3. **一台 client 一个顶层目录**，各自独立，不做跨机路径合并。一台 client 共享多个目录时，这些目录挂在它自己这一层下面。

4. **聚合是选入的**：client 配置里一个开关，开了才被聚合。

5. **全局只允许一台打开这个开关**，第二台试图打开时由 server 拒绝。

6. **观察者也共享自己**，以普通成员的身份出现在自己的树里。

7. **v1 不做安全**：不做认证、授权、传输加密，先把主流程跑通。这意味着 **v1 只能跑在可信网络里**。

8. **观察者那边是真内核挂载点**，任意程序双击就能打开，而不是 peerfold 自带一个浏览界面。

9. **v1 的平台范围是 Windows + Linux**，macOS 推后。

   附带一个结论：**只有观察者那台需要装驱动**，供货方那几台什么都不用装。Linux 侧是 FUSE，Windows 侧是 WinFsp——后者是第三方内核驱动，观察者得先自己装上。

## 四、我替你做的决定

这些**是我拍的，不是你说过的**，随时可以推翻。

1. **语言用 Go**：单文件静态二进制、三平台交叉编译、fsnotify / FUSE / WebDAV 生态齐全，Syncthing 和 rclone 都是这个路子。

2. **一个二进制，两个子命令**：`peerfold server` / `peerfold client`，共用一份配置文件。

3. **v1 不做开机自启，也不做系统服务**：以当前登录用户身份跑。这条同时定死了写回文件的属主——就是你自己的用户，不会变成 root / SYSTEM。

4. **加入一台机器是一条命令**，顺手把配置落盘：
   ```
   peerfold client --server 192.168.1.10:7000 --share ~/Documents
   ```

5. **写回采用整文件回写，不做分页。** 因为 vim / VS Code / Office 保存的真实形态都是"写临时文件再改名覆盖"。挂载层把 `rename` 翻译成"整文件回写 + 原子替换"之后，写回逻辑反而最简单、也最不容易丢数据。代价是改一个字节也要传整个文件。

6. **保存是同步的，不做观察者侧暂存队列。** 编辑器 close/rename 返回成功时，字节必须已经落到供货方磁盘上；供货方离线、权限不足、磁盘满，就在那个调用上如实报错。宁可保存慢、甚至保存失败，也不接受"以为存上了其实没有"。

7. **索引里只装活着的 client。** 某台 client 掉线，它的子树立刻从树上消失，不留幽灵条目；它回来再重新长出来。server 重启后由各 client 重连重建索引。这条同时把"树说谎"定义清楚了：树里出现的路径，读它必须能成功。

8. **索引重建期间树是即时可见、逐步长出来的**，不会"扫完才出现"。一个 client 有 50 万个文件时，你看到的是它一点点长出来，而不是先空半天。

9. **索引只负责列表；`open` 时向归属 client 复核一次 size/mtime。** 两个理由：`stat` 的 size 错了会让靠预分配和 seek 的程序损坏文件；而复核开销只落在真正被打开的文件上。

10. **反向实时必须靠主动失效内核缓存来实现。** 只更新 server 的索引是不够的——挂载层必须调用 FUSE / WinFsp 的失效通知，否则内核页缓存会继续把旧内容喂给你，那就等于树说谎。这是"实时"这条需求的真正着力点。

11. **挂载点永不进索引。** 这是第三节第 6 条的必然推论：否则观察者会把自己挂着的树当成自己的文件再共享出去，无限套娃。实现上，观察者必须拒绝索引自己的挂载点路径。

12. **单聚合由 server 把关**：server 记住当前观察者，只有当它断开之后，另一个开着开关的 client 才能接任。第二台开着开关但被拒的，**降级成普通供货方继续跑**，并在日志里说明，不拒绝启动。

13. **client 名字默认取主机名**，由 server 校验唯一；撞车了要求显式指定名字。

14. **v1 不做忽略规则**，供货方目录里有什么就照实呈现，包括编辑器留下的临时文件、构建产物。

## 五、v1 的边界

**总原则：在聚合树上操作，应该和操作本地文件没有区别——除了物理上做不到的那些。**

**本机范围内的常规操作，全部支持**：新建文件、新建目录、覆盖写（含截断）、重命名、删除（文件与目录）、在同一个 client 的目录树内移动。

注意这一组是省不掉的：编辑器保存走的正是"新建临时文件 → 写 → 改名覆盖"，`git`、解压、装包这类操作又会顺手建目录、改文件名、删文件。少了任何一个，"拿它当本地文件用"就不成立。

**物理上做不到的，明确不做**：

- **跨机器 `mv`**：在两个不同物理主机之间没法原子搬动，返回 `EXDEV`。程序看到这个会自己退化成"复制 + 删除"，这是标准行为，不算缺陷。
- **`chmod` / `chown` / 硬链接**：Windows 没有 POSIX mode，两平台对不齐，语义无法诚实表达。

**留给实现者**：供货方一侧的符号链接怎么呈现（最省事的做法是跟随目标、当成普通文件）。

**读操作**：支持随机访问和 `seek`（内部按范围拉取），不支持写 `mmap`。

**文件名**：以 UTF-8 字节串作为主键，不做归一化、不改写。大小写不敏感的目标平台上，仅大小写不同的重名是已知限制。

**规模目标**：≤ 10 台 client，单 client ≤ 100 万文件。

**冲突**：后写覆盖（last-write-wins）。观察者整文件回写时，会盖掉供货方在这期间对同一文件做的修改。这是 v1 明知的取舍，**不是"悄悄丢数据"**——它写在这里，也应当写进用户文档。

## 六、v1 明确不做

- 认证、授权、传输加密
- macOS 支持（推后到 v1 之后）
- 跨机器 `mv`、`chmod` / `chown` / 硬链接（见第五节）
- 写 `mmap`
- 并发编辑同一文件的冲突检测与合并（v1 为后写覆盖，见第五节）
- 分页 / 增量写回
- 内容缓存（v1 先纯流转；大文件打开会明显慢，以后加）
- "同步盘"模式（本地留一份副本）
- 多个观察者
- 挂载驱动的打包与友好安装流程（Windows 侧要求观察者自己先装好 WinFsp）

---

## 七、明确要避免的（技术上能跑也算失败）

- **树说谎**：树里出现的路径读不到，或者 `stat` 出来的大小是错的 —— 很多程序靠 size 预分配和 seek，错了会直接损坏文件。
- **保存悄悄丢数据**：本地看起来保存成功，但原机器上什么都没变。
- **误删真文件**：挂载层现在能建、能删、能改名，而它作用的是别人机器上的真磁盘。一个 bug 就是真的丢文件，不是丢副本。
- **套娃**：挂载点出现在自己的树里。
- **退化成同步盘**：必须先搬完全部文件才能看见东西。

## 八、留给实现者的

以下是我故意不定的，实现者自行拿主意：

- 线上协议的具体编解码与帧格式
- 全局索引的数据结构与存放方式
- 内容缓存的策略（v1 建议先纯流转、不做缓存）
- 配置文件的具体字段与格式
- CLI 参数的具体命名
- 索引重建的分批大小与推送节奏
- 挂载点在两平台的具体落点（Linux 是目录，Windows 是盘符还是目录）
- 供货方一侧符号链接的呈现方式
- 目录操作的顺序与失败回滚（一次 `rename` 涉及两个节点，一半成功一半失败时怎么收场）

## 九、主流程（形态层面的六步）

1. **装与起** —— server 和 client 都是常驻进程
2. **client 上线** —— 告诉 server：我是谁、我共享哪些目录
3. **看到列表** —— 所有机器的文件在观察者本地实时呈现
4. **读** —— 打开某台机器上的某个文件
5. **写回** —— 改完保存，那台机器上那个文件真的变了
6. **反向实时** —— 原机器自己产生的变化，立刻出现在观察者这边
