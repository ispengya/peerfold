### 这份 v2 改了什么（一句话）

v1 版本文档**设计在一个并不存在的 viewer API 之上**：它承诺了"open 时向属主复核
size/mtime"、承诺了"察觉丢更新后整体作废"，而这两件事 v1 的线上格式和 `viewer`
**都做不到**。一个独立的评审子代理逐条核过代码之后指出了这一点。第十四节是完整
的逐条回复，其中**5 条接受、1 条部分反驳、3 条澄清**。

主要变化：新增 **D11（离线与重连）**、**D12（符号链接）**，改写 **D3（缓冲的两级
上限）** 与 **D5（丢更新怎么察觉）**，**D4 被 §六 取代**（元数据超时不再是 0），
并把"协议不动"这条约束**降级为"线上格式不动，但允许给 `Err` 文本加机器可读
前缀"**（D6）。

## 一、这一层是什么，为什么是最后一块

v1 核心（第一份计划）已经把整条链路做通了：星型拓扑、全局索引、列举、读、写回、
变更传播、以及一个 `viewer` 连接角色。但它的入口是**命令行** —— `peerfold ls`、
`cat`、`put`。

设计文档 §1 把"什么算成功"写得很具体：

> 在开了聚合开关的那台机器上：`ls` 立刻列出所有其他机器的文件；`cat` 一个远端文件
> 能出内容；**用编辑器改完保存**，去那台机器上 `cat` 同一个文件，内容真的变了。

前两句 v1 已经做到。**第三句只有挂载层能成立** —— 因为编辑器不认 `peerfold put`，
它认文件系统。挂载层就是"让这台机器上的普通程序以为远端文件是本地文件"的那一层。

做完这一层，peerfold 变成可以天天用的东西：打开一个文件夹、双击、编辑、保存。
**这就是 MVP 的全部。** 之后再要的东西（认证、缓存、macOS、多观察者、开机自启）
都是后续优化，本文一条都不做（见第十一节）。

## 二、范围

### 做

- 观察者本机一个**真内核挂载点**，普通程序无需知道 peerfold 的存在
- **Linux（FUSE）完整交付**；Windows（WinFsp）见 D13 —— 它是**本计划的待定项**，
  不是已承诺项
- 完整的文件系统操作：`getattr` `readdir` `open` `read` `write` `create`
  `truncate` `mkdir` `unlink` `rmdir` `rename` `fsync` `statfs`
- 随机访问与 `seek`
- 写回是整文件原子替换（复用 v1 的写路径）
- 反向实时：别处的变化反映到挂载点，**包含内核缓存的主动失效**
- **离线与重连**（D11）：server 重启或网络抖动之后，挂载点自己恢复
- 跨机 / 跨共享 `rename` 返回 `EXDEV`
- 套娃与递归的防护
- `peerfold mount` 子命令

### 不做（明确划出，见第十一节）

- 跨 open 的持久内容缓存
- `chmod` / `chown` / 硬链接 / 写 `mmap`
- **符号链接的忠实呈现** —— 而且见 D12：v1 现在对符号链接的行为是**不一致的**，
  挂载层必须**拒绝**而不是"当普通文件"
- 认证、加密
- macOS
- 开机自启 / 系统服务
- 挂载驱动的打包与安装引导

## 三、约束（不是选择，是给定条件）

1. **线上格式不改；`Err` 文本的**内容**可以作为机器可读的载体（D6）。**
   挂载层复用 `viewer` 角色，不改帧结构、不改 `Kind` 表、不改 `NodeJSON` 的字段。
   但"错误文本"这条我原来写得太严：v1 的错误就是 `err.Error()` 的字符串，而
   **owner 的底层错误是操作系统相关的**（Windows 上文件不存在说
   "The system cannot find the file specified"，Linux 说 "no such file or
   directory"）。所以 D6 允许给 `Err` 字段**加一个稳定的前缀 token**，
   而不新增字段、不改结构。这是**对第一份计划那句"不改协议"的收窄解释**：
   改的是字符串的约定，不是格式。
2. **`viewer` 一次只允许一个请求在飞。** `stream()` 用一个容量 1 的令牌把请求
   串起来；协议是单连接、控制帧与数据帧严格交替，两个并发请求会把一个答复读成
   另一个的。
3. **`viewer` 的事件通道是非阻塞的，满了就丢 —— 而且丢得没有痕迹。**
   `emit` 用一个带 `default:` 的 `select`，丢弃时**不计数、不报错、没有序号**
   （`viewer.go:657-670`）。更糟的一条：`server.broadcast` 在推送失败
   （`eventBroadcastTimeout` = 5 秒）时**把这个 watcher 永久删除**
   （`server.go:576-584`），而**连接本身仍然可用** —— 于是 `List`/`Read` 照常成功，
   远端变化却**永远不再到达**。D5 必须正面处理这个"静默变聋"。
4. **`viewer.Read` 的 `n` 用负数表示"读到结尾"**，不是 `n == 0`。
   `n == 0` 返回空切片而**不是错误** —— 看起来正像一个空文件。挂载层必须传 `-1`
   或正数。
5. **写回是整文件回写**，`put` 的语义就是"整个文件的内容"。没有部分写的线上表达。
   所以 `write` 的中间状态**无法增量上传**，`fsync` 的含义只能是"现在整文件回写"。
6. **v1 没有定期重扫。** 索引由连接时那一次上传播种，之后只被 fsnotify 推动。
   丢掉的变更**不会**自愈（要等同一个路径再变，或 client 重连）。
7. **索引只装活着的 client。** 掉线即子树消失，不留幽灵条目。
   **但是**：client 上下线**不广播**（`server.go:270-277` 只做 `RemoveClient` +
   `Unregister`，`broadcast` 只在 `applyEvent` 里被调），所以挂载层**不会**收到通知
   —— 见 D5 与 D11。
8. 本机环境：**没有 C 工具链**，`-race` 不可用。
   **但是 `GOOS=linux CGO_ENABLED=0 go build ./...` 是通的**（实测），所以
   **Linux 侧能编译、能跑单元测试，只是不能真挂载**。见 D13。
9. **索引里的元数据只有"事件到达时的快照"这一个新鲜度。** 线上**有**元数据
   （`node.Node` 带 `Size`/`Mode`/`Mtime`，`List` 会返回），但它来自 server 的
   **索引**，**永远不是从属主的磁盘现读的** —— 线上没有 `stat` 这个 `Kind`
   （`Kind` 表里只有 `hello/tree_batch/tree_done/event/list/list_ok/read/read_ok/
   write/write_ok/mkdir/rename/remove`）。见 §六。

## 四、我替你做的主决定

这一节是全文的核心。每条给"决定 / 为什么 / 判错的代价"。

### D1 挂载点落点：两平台都用目录，都放用户主目录下

- **Linux**：`~/peerfold`
- **Windows**：`%USERPROFILE%\peerfold`

不占盘符、不落在驱动器根、两平台形态一致（不用维护两套）。

**为什么不用盘符**：那是唯一的备选，好处是它**不是任何目录的孩子** —— 遍历
`C:\` 永远不会撞上它。但代价是平台差异：Windows 与 Linux 的挂载点形态会分叉，
而收益只覆盖"遍历那个盘"这一种情形。我选择一致性。

**必须同时成立的硬条件**：挂载点**不能在任何共享目录里面**。所以：
- 默认落点在任何共享之外
- `--exclude` 必须真接上（v1 里它生产代码**永远是 nil**，没有任何 flag 能到它）
- 挂载时**主动检查**：如果挂载点落在某个共享子树内，**拒绝挂载并说清楚**，
  而不是挂上去以后套娃

**判错的代价**：一个遍历用户主目录的程序（备份、索引器、`tree ~`）会走进挂载点
并开始枚举整棵远端树，而每个 `stat` 都是一次网络往返。这是**已知要接受的代价**，
不是我没看见。

### D2 模块结构：可移植的核 + 两个薄壳，用文件名后缀分平台

```
internal/mount/
  mount.go          可移植核：路径解析、操作语义、错误映射、缓冲
  mount_test.go     与平台无关的测试（用假的 viewer 接口）
  fuse_linux.go     FUSE 绑定（GOOS=linux 自动选中，不用 build tag）
  winfsp_windows.go WinFsp 绑定（GOOS=windows 自动选中）
```

**为什么**：绝大部分逻辑（路径怎么拆、`getattr` 拿什么、`rename` 什么时候该
`EXDEV`、缓冲怎么淘汰）与平台无关。把它放进可移植核，意味着**这部分能在没有
FUSE 的机器上被完整测试** —— 而本机恰好没有 FUSE。两个薄壳只做"把内核的调用
翻译成核的调用"。

**不用 build tag**：Go 的 `_linux.go` / `_windows.go` 后缀自动生效，比 build tag
更少出错。**这一点我在写文档时实测验证过**（用一个临时 module 交叉编译）：

- `GOOS=linux CGO_ENABLED=0`：`bazil.org/fuse` 与 `github.com/hanwen/go-fuse/v2`
  都能**通过编译** —— 所以两边都**不需要 C 工具链**
- `GOOS=windows`：那个 linux-only 的文件被**整体排除**，`go build ./...` 报
  "matched no packages"，**一个字节的 FUSE 代码都不进 Windows 构建**

**结论**：仓库可以**保持一份 `go.mod`、一份 `go.sum`**，Linux 专属依赖只被
linux-only 的文件引用，Windows 构建绕开它。不需要按平台拆 module。
`internal/viewer` 的间接依赖是 `golang.org/x/sys v0.13.0`，而 FUSE 需要
`v0.28.0` —— 只是**升一个版本**，不引入新的依赖树。

**判错的代价**：如果两个平台的语义分歧比预期大，核会被撑大或者出现 `if GOOS`
分支。缓解办法是**先只做 Linux**（见 D7），把核的形状用真实需求定下来，再接
Windows。

### D3 读：每次 open 建立块缓冲，**两级上限**

这是本文最需要精细的一条，也是我上一轮口头推荐里**说漏了上限**的那条。

**机制**：
- 一个 open 对应一个 `buffer`，块大小 **128 KiB**（见下）
- `read(off, n)` 命中已缓冲的块就直接返回；未命中就向属主取那一块，存下来
- 同一个 open 内的重复读、顺序读、随机读都走这个缓冲
- **单一 open 的上限**：默认 **64 MiB**，`--buffer` 覆盖。超限在本 open 内按 LRU 淘汰
- **所有 open 合计的全局上限**：默认 **256 MiB**，`--buffer-total` 覆盖。超限时
  淘汰**别的 open** 的块（优先淘汰最久未用的整个 open 的缓冲）
- close 时整个丢掉

**为什么是两级（这里我 v1 版写错了）**：v1 版说"分块 + LRU 上限把内存钉死在
64 MiB，无论文件多大" —— 这句**只对一个文件成立**。N 个并发 open 就是 N × 64 MiB，
上不封顶，而 CLI 上只有一个旋钮。评审子代理指出了这一点，是对的。
**只有全局上限才真正让内存有界**；单一 open 的上限只是"一个特别大的文件别把别人
挤死"。两个都要，且两个都要能测（见 §七的内存压力测试）。

**为什么块而不是整文件**：整文件缓冲对一个 10 GB 的文件会让挂载进程 OOM。分块 +
两级上限让内存**真正有界**，同时"顺序读"仍然只需每个块一次往返。

**为什么 128 KiB**：`proto.MaxPayload` 是 1 MiB，而探针实测每帧成本随帧大小涨
（64 KiB 块 533µs、256 KiB 块 1.0ms、1 MiB 块 3.0ms/次）。1 MiB 块**正好顶到
帧上限**，是最坏的选择。128 KiB 在安全余量之内。

**为什么必须分块而不是"流式顺序读"**：`seek` 是设计文档 §5 明确要求的，而纯流式
无法回退。分块天然支持随机访问。

**这不是缓存**：它的生命周期是**一个 open**，短于任何远端变化能到达的时间窗口，
所以不需要失效机制。设计文档 §6 的"v1 不缓存"约束的是**跨 open 的持久缓存**，
本条不违反它。

**判错的代价**：上限太小 → 大文件顺序读反复淘汰块（退化成每次都往返）；太大 →
内存压力。64 MiB / 256 MiB 都是拍的，**应当实测后再定**。真正修法是跨 open 的
持久缓存，那需要主动失效配套，留给后续。

### D4 元数据：**有界的新鲜度**，不是"超时为 0"

- `attr_timeout` / `entry_timeout` 设为**一个短而明确的值**（初值 1 秒），并且
  **由 D5 的主动失效来提前作废**
- `negative_timeout` 设为 0（宁可不缓存"不存在"，因为一个不存在的判断错得比存在更痛）

**为什么不是 0（这里我 v1 版自相矛盾，评审子代理指出了）**：v1 版 D4 说
"超时全 0，所以每次 `getattr` 都是一次往返"，而 D3 给缓冲的理由里却写着
"缓存让 `getattr` 不用每次往返"。**两个说法不可能同时是本条的理由。** 正确的是：

> **超时的作用不是"正确性"，而是"丢更新之后的兜底上限"。**

因为约束 3 证明了挂载层**可能静默变聋**（`emit` 丢包无痕迹、`broadcast` 永久删
watcher）。一个正的超时意味着"**即使通知机制整个失效，树最长也只错 1 秒**" ——
这是唯一能在不改协议的前提下给"树说谎"定上界的手段。超时 0 会让挂载层在变聋之后
**永久**服务陈旧元数据，那比错 1 秒严重得多。

**代价要如实说**：目录列举会明显变慢（一次 `readdir` 之后内核会为每个条目
`getattr`，每个都可能在超时过期后回到网络）。这是**接受的**，因为正确性优先。

**判错的代价**：1 秒这个数字是拍的。它同时是"性能损失"和"错误窗口"两个东西的
旋钮，方向相反 —— 真实数字应当**实测后**再定，而且很可能应当分成两个旋钮
（目录项 / 属性），但现在先给一个。

### D5 反向实时：主动失效 + **丢更新的探测**，而不是靠超时

- 挂载层订阅 `viewer.Watch()` 的事件流
- 收到某个路径的更新 → 调用平台的内核失效接口（Linux `fuse_lowlevel_notify_inval_inode`
  与 `..._inval_entry`；WinFsp 的对应接口）
- 失效**失败或不可用**时，必须**如实降级并在日志里说明**，不能假装成功

**为什么必须做**：设计文档 §4.10 写得很直白 —— "只更新 server 的索引是不够的，
挂载层必须调用 FUSE / WinFsp 的失效通知，否则内核页缓存会继续把旧内容喂给你，
那就等于树说谎"。**这是"实时"这条需求的真正着力点**，也是本文最大的一块工程风险。

#### 丢更新怎么察觉（v1 版这条是空话，评审子代理指出了）

v1 版写"挂载层必须在察觉到自己可能丢过更新时整体作废元数据"，但
**没有任何东西会告诉它丢了** —— `emit` 丢包不计数、`EventBody` 没有序号、`server`
删 watcher 也不通知。所以这条必须落到具体机制上。三件事一起做：

1. **给 `EventBody` 加一个单调序号**（`Seq uint64`，纯增量字段，不改已有字段）。
   `viewer.emit` 在**丢弃**时记下"我丢过"，`Watch` 侧多暴露一个"最近的序号"或一个
   丢包计数。挂载层看到**序号跳变**就知道"中间有批没收到"。
   *这是本文唯一一处需要动 `proto` 的地方，且是**加字段**，不是改语义*。代价：
   一个有测试的失败信号，换来"能知道自己瞎了"。
2. **给 watcher 加活性信号**。`server.broadcast` 现在失败即**永久删除** watcher。
   最小修法：**不删**，改为记下这个 watcher 已经追不上，并给它发一个"你落后了"的
   事件（或直接在连接上回一个错误让它重连）。**在任何情况下都不能"悄悄变聋"** ——
   这是比丢一条更新严重得多的失败模式。
3. **兜底仍靠 D4 的超时**：上面的机制**没做或失效**时，树最多错 1 秒。

#### "整体作废"在 Linux 上到底是什么

评审子代理说得对：**FUSE 没有"作废整个文件系统"这个原语**，只有 per-inode /
per-entry 通知。所以"整体作废"只能实现成：

- 挂载层维护一张**"我曾经交给内核的 inode/路径"表**
- 探测到丢更新时，遍历这张表，对每一项发一次失效
- 表本身要有上限（否则长时间运行的挂载会攒出一张无限的表）—— 超过上限时
  **如实记录"无法完整作废"**，而不是假装做到了

**判错的代价**：失效是对的但性能可能不够（每个事件一次系统调用）；加上"我交出去
过什么"这张表，挂载层多一份状态。这份状态本身可能出错，所以它要有测试。

### D6 错误码：在 viewer 内部加定点错误 + 一张映射表，不动协议

**问题**：内核要 `errno`（`ENOENT`、`EEXIST`、`ENOTEMPTY`、`EXDEV`、`EACCES`…），
而 v1 的错误**主体是自由文本字符串**。只有跨 client 的 `rename` 是定点错误
（`viewer.ErrCrossClient`）。从字符串猜 `errno` 不可靠。

**做法**：
1. 在 `internal/viewer` 增加一组定点错误，与 `ErrCrossClient` 同一个先例：
   `ErrNotFound`、`ErrNotDir`、`ErrIsDir`、`ErrExists`、`ErrNotEmpty`、
   `ErrPermission`、`ErrOffline`
2. 加一个**唯一的**翻译点 `errnoFor(err) error`：把上面的定点错误映射成
   `syscall.Errno`
3. 挂载层只调 `errnoFor`，**不允许**在别处出现字符串比较

**为什么不能只靠"匹配现有文本"（v1 版这条是错的，评审子代理指出了）**：
属主的底层错误是**操作系统相关且本地化的**。同一个"文件不存在"，Linux 属主回
"no such file or directory"，Windows 属主回 "The system cannot find the file
specified"；再经过 `"viewer: "` 包装和 `server` 的重包装
（`router.go` 的 `client: %q is not empty: refusing to remove ...`）。
**一张匹配另一种操作系统的本地化字符串的表，是不可维护的。**

**所以：`Err` 字段的内容里放一个稳定 token。** 约定形如

```
<token>: <人类可读的原因>
```

例如 `enoent: no such file or directory`、`enotempty: client "win" ...`。
- `errnoFor` 只认**前缀 token**，**绝不**匹配人类可读部分
- token 集合是**封闭的、有测试的**；认不出的 token → `EIO`（保守兜底）
- 人类可读部分原样保留，所以 v1 已有的 CLI 输出**不会变**

**代价（如实说）**：这需要在 `internal/client` 与 `internal/server` 里**各改几处
构造错误的地方**，把它们从 `fmt.Errorf("...")` 改成带 token 的形式。**这是对第
一份计划"不改协议"那句的收窄解释** —— 改的是**字符串的约定**，不是帧格式、
不是字段、不是 `Kind`。我认为这个代价是值得的：另一条路是"靠猜另一种语言的
字符串"，那条路在真实使用中一定会出错，而其中有些错误是 `ENOTEMPTY` 与
`ENOENT` 的区别 —— 猜错了就是**删错东西**。

**判错的代价**：漏掉一个错误构造点 → 那个错误退化成 `EIO`。方向是安全的
（报错而不是误判成功），而且**是可以被测试发现**的：§七 要求穷举 linter 式的测试
断言每个已知错误路径都带 token。

### D7 交付顺序：**先 Linux，跑通整条链路，Windows 见 D13**

1. 先做 Linux FUSE，把挂载、读、写回、失效、套娃检测**全部真实跑通**
2. 核的形状由真实需求定下来之后，再接 WinFsp（**但 D13 说这件事的可行性待定**）

**为什么**：两平台同时开工，出问题时分不清是**模型**错了还是**某个平台**错了。
Linux 侧不需要装内核驱动（FUSE 是内核自带的），所以它能先独立验证。

**判错的代价**：Windows 用户要等更久。这是**有意**的取舍。

### D11 离线与重连：**自己恢复，且把在飞的脏数据说清楚**

`viewer.Dial` 只连一次，**没有重连**。pump 退出之后 `stream()` 就直接调用了
（reader=false），所以调用会**报错而不是挂死** —— 好的一点是不会卡住内核。
但结果是：**server 重启一次，挂载点就废了，直到用户手动静卸载重挂。**

**决定**：

1. **挂载层自带一个 supervisor**：连接断了就按退避重连（首次 1 秒，倍增到上限
   30 秒，带抖动）
2. **重连成功后必须做三件事**（顺序不能换）：
   - 重新 `Watch()`（旧的 watcher 在 server 那边已经没了）
   - 把**全部**已知元数据与内容标记为不可信（用 D5 的"我曾经交出去的表"作废内核）
   - 再开始服务请求
3. **重连期间**：操作返回 `EIO`（不是 `ENOENT`）。**`ENOENT` 是错的** —— 它会让
   程序以为文件被删了，可能触发"那就删掉本地副本"这类破坏性反应。
4. **重连失败超过阈值**（初值 2 分钟）→ **卸载自己并退出**，并把原因写清楚。
   一个永远返回 `EIO` 的挂载点是**更坏**的结局：用户以为它在工作。

#### 断线时在飞的脏 open（这是本决定里最危险的部分）

一个 open 已经改过内容但还没回写，这时连接断了。**我选：如实报错，绝不假装成功。**

- 该 open 之后的任何 `write`/`release`/`fsync` 都返回 `EIO`
- **不**把内存里的脏字节"等重连之后再写" —— 那个内容是基于断线前的状态做的
  读-改-写，重连之后远端可能已经变了，写回去就是**静默覆盖别人的修改**
- 日志里明确指出**哪个路径**的修改被丢弃了，让用户能重做

**为什么这比"自动重试回写"好**：自动重试看起来更友好，但它把"数据可能冲突"这个
事实藏起来了，而设计文档 §7 把"保存悄悄丢数据"列为必须避免的失败。**宁可让用户
重做一次，不可让他以为存好了。**

**判错的代价**：退避参数、超时阈值都是拍的。状态机本身会增加实现的复杂度与一整类
测试（§七单独列）。

### D12 符号链接：**必须拒绝，而且这是修一个 v1 的真实不一致**

评审子代理在这一点上是对的，这是本文里**唯一一个"v1 已经存在的数据损坏路径"**。

**v1 现在的实际行为（三条互相矛盾）**：
- `shares.go` 的扫描用 `WalkDir` 的 `DirEntry.Info()`，那是 **`lstat`** → 符号链接
  被索引成 `KindFile`，`Size` = **链接目标字符串的长度**（比如 9 字节）
- `watch.go` **丢弃**符号链接的 fsnotify 事件
- 属主的 `ReadAt` 用 `os.Open`，那是 **`follow`** → 返回**目标文件的内容**

**后果**：同一个路径，`getattr` 说 9 字节，`read` 返回 5000 字节。内核按 `i_size`
截断读，所以：
- 只读：看起来像"一个 9 字节的怪文件"
- **读-改-写**：程序读 9 字节、改写、写回 → 那 9 字节**覆盖掉目标文件**
  （通过整文件 `put` 的原子替换）。**这是真丢数据，而且发生在很常见的场景里**
  （代码仓库、家目录里到处是符号链接）

**决定**：**挂载层识别符号链接并拒绝**，`open` 返回 `ELOOP`，
`getattr`/`readdir` 把它呈现成"不是普通文件"。**不是"当普通文件"，也不是
"跟随目标"。**

**怎么做**：`node.Node` 已经有 `Mode uint32` 字段（线上已有，扫描时填的是
`lstat` 的 mode），所以**链接位已经在数据里了**，挂载层读 `Mode` 就能判断，
**不需要改协议**。这需要核实一件事：`shares.go` 填 `Mode` 时是否保留了
`os.ModeSymlink` 位 —— **如果没保留，那是本计划要修的客户端侧改动**（很小，
但在已合并的包里，必须单独列成一个任务并在计划里说明）。

**为什么不选"跟随目标、当普通文件"**：那要求 `Size`/`Mtime` 都改成目标的值，
也就是扫描端必须 `stat`（follow）而不是 `lstat` —— 那是**改 client 的扫描语义**，
影响面远大于挂载层拒绝。而且它会让"链接目标在共享之外"的情形把外部文件暴露出来
（现有的 `LocalPath` 是词法的，见 v1 的已知小开口）。**拒绝是更小、更安全的改动。**

**判错的代价**：用户看到 `ELOOP` 而不是能用。这是**有意的** —— 报错比悄悄损坏好。

### D13 Windows 侧：**本计划先不承诺**

评审子代理指出：主流的 Go WinFsp 绑定 `github.com/winfsp/cgofuse`
**是 cgo 的**，而本机 `CGO_ENABLED=0` 且没有 C 编译器 —— 和 `-race` 不可用是
同一个原因。**Windows 壳在这台机器上无法编译，更无法挂载测试（也没装驱动）。**

**决定**：
- **本计划交付 Linux 侧，完整并经过真实的挂载测试**
- 可移植核写成平台无关的（D2），**为 Windows 留好接缝**，但**不承诺**它在这台
  机器上能编译
- §十二 的成功标准**去掉"两平台都通过"那一条**，改为"Linux 通过；Windows 是
  后续计划，前提是先解决 C 工具链与驱动安装"

**三个选项里我选哪个，以及为什么不选另两个**：
- 选 **(c) 本计划不含 Windows** —— 因为一个"写了但从没编译过"的平台壳是**负债**
  （它会腐烂、会给人"支持 Windows"的错觉），而(b) 正是这个负债
- 不选 **(a) 装 mingw** —— 那是一个**独立的环境建设决定**，涉及这台机器上装编译器，
  应当单独提出来由你决定，而不是塞进挂载层计划里当隐含前提

**这一条需要你拍板**（见 §十五的开放问题）。

### D8 并发：挂载层自己排队；不够就开第二条 viewer 连接

*（编号说明：D8–D10 是 v1 版原有的三条；D11–D13 是 v2 修订时新增的，
排在 D7 之后以免打乱评审所对照的编号。三组按内容互相引用，编号不表示顺序。）*

- 所有 viewer 调用经挂载层的**一个队列**串行化
- 不做请求流水线（协议不容许，见约束 2）
- 如果测量显示单连接是瓶颈，**开第二条 viewer 连接**，而不是改协议层的单读者约束

**为什么**：单读者约束是帧边界正确性所依赖的。动它的风险远大于收益，而"多开一条
连接"是纯增加、零风险。

**判错的代价**：一个会话。串行化会把内核的并发压成顺序，可能影响吞吐。

### D9 套娃与递归防护：三层

1. **落点检查**（挂载时）：挂载点在任一共享子树内 → 拒绝挂载（见 D1）
2. **`--exclude` 真接上**：用户自己把挂载点包进共享时，扫描时跳过
3. **视图识别**：挂载点的根放一个标记（`.peerfold-root`），并且 `statfs` 报告一个
   可识别的文件系统类型 / 特征，让遍历器**能**发现"我跨进了另一个文件系统"

**为什么三层**：第 1 层防最常见的错，第 2 层防用户不小心，第 3 层防"两个 peerfold
实例互挂"。前两层是**默认生效**的，第 3 层要求遍历器愿意看一眼 —— 这是**部分**
防护，不是保证，如实记录。

**Linux 有一个免费的额外判据**：挂载点下所有条目的 `st_dev` 等于这个 FUSE 文件
系统的设备号，与外面必然不同，遍历器不读任何标记文件就能发现跨了文件系统。
**Windows 没有等价物**（WinFsp 挂成目录时卷序列号语义更弱、更容易被忽略），
所以 Windows 上只能靠标记。**这是两个平台在"防递归"上真实的能力差异**，不是我
偷懒。

**判错的代价**：第 3 层防不住不读标记的遍历器。

### D10 写入路径：复用 v1，不发明新东西

- `create` → **一次内容为空的 `put`**。不需要新协议：`WriteModePut` 的语义就是
  "替换目标，不存在就创建"，所以"建一个空文件"就是"写一个空文件"。这也是
  POSIX 的语义（`open(O_CREAT)` 的目标是让文件存在，不是让它非空）
- `write` → 记下"这个 open 是脏的"
- `release` / `flush` → 脏则**整文件回写**（v1 的 `put` 语义：临时文件 → `Sync` →
  `Sync` 父目录 → 原子 `rename`）
- `truncate` → 同一条路（读、截断、回写）

**为什么用 `put` 而不是某个"create"调用**：我核过协议，**没有** `KindCreate`（我在
第一份计划的交接文档里看到过这个说法，那是错的 —— `Kind` 表里只有
`hello/tree_batch/tree_done/event/list/list_ok/read/read_ok/write/write_ok/mkdir/
rename/remove`）。`internal/client/fsops.go` 里那个 `FS.Create` 确实存在、也确实
没有生产调用者，但**挂载层不需要它** —— 空 `put` 走的是已有的 `KindWrite` 路径，
零协议改动。**这一条纠正了我自己先前的说法。**

**为什么是 release 而不是 write**：设计文档 §4.6 要求"编辑器 close/rename 返回
成功时，字节必须已经落到供货方磁盘上"。整文件回写意味着 `write` 的中间状态无法
增量上传，所以正确的位置是**关闭时**一次写完。这也和编辑器的真实形态吻合（它写
临时文件再改名）。

**这意味着**：一个 open 期间的所有写在内存里积累，close 时一次性回写。所以
**写缓冲也有上限**，超限必须走"边写边回写"或者如实报 `ENOSPC`/错误 ——
**不能悄悄截断用户的文件**。

#### 哪些操作必须**强制**回写（v1 版只写了 close，评审子代理列全了）

v1 版只覆盖了 `release`/`flush`，而**内核可以在不 close 的情况下要求落盘**。
以下每一条都必须在返回成功**之前**完成回写，否则就是"保存悄悄丢数据"：

| 操作 | 为什么必须强制 | 不做的后果 |
|---|---|---|
| `fsync` | 程序自己的持久点，它返回成功就意味着"已经落盘" | 程序以为存好了，关机就没了 |
| `rename`（涉及脏 open 的文件） | **编辑器 temp→target 就是这个模式** | 改完重命名，内容还在内存里 |
| `unlink`（脏 open 的文件） | 删之前它可能刚被写过 | 静默丢掉最后一次修改 |
| `truncate`（脏 open 的文件） | 截断的基准是内存里的脏内容，不是远端旧内容 | 截断结果错，且可能覆盖别人 |
| **卸载 / SIGINT**，仍有脏 open | 退出前的最后一次机会 | 内存里的修改直接消失 |

**设计含义**：可移植核必须暴露一个**"先冲刷（flush）再变更（mutate）"**的接口，
而不是"只有 close 才冲刷"。所有会改变一个路径的操作，都要先问一遍
"这个路径有脏 open 吗"。

**这一条是本文最危险的部分**，所以 §七 的"安全测试"必须逐条覆盖上表 —— 每一条
都要有"失败时目标未被修改"的断言。

**判错的代价**：这是**最危险**的一条。设计文档 §7：挂载层作用的是"别人机器上的
真磁盘。一个 bug 就是真的丢文件，不是丢副本"。

## 六、元数据的两件事：怎么取，以及"复核"这件事做不到

### 取单个节点：用 `List(parent)`，不加线上的 `stat`

`getattr` 需要"路径 → 属性"，而 v1 的 `viewer` 只有 `List(父目录)`。

**决定**：挂载层用 `List(parent)` 然后取最后一段，**不在线上加 `stat`**。

**为什么**：加线上 `stat` 要动 `Kind` 表，而那是格式改动。用 `List` 取一项在语义上
正确 —— `List` 返回的 `node.Node` **已经带** `Size`/`Mode`/`Mtime`，索引里那一项
就是"server 知道的真相"。代价是多列出整个父目录。

### "open 时向属主复核 size/mtime" —— 这一条**做不到**，而且是我 v1 版的错

**v1 版 §九 里我写过"open 时向属主复核 size/mtime"，那是错的。** 它抄自冻结设计
文档 §4.9（"open 时向属主复核大小和 mtime"），但**那份文档描述的是一个 v1 没有
实现的协议**：

- 线上**没有** `stat` 这个 `Kind`
- 读的答复**只带内容**：属主在 `client.go:453` 明确**丢弃**了 `FileInfo`
  （`data, _, err = c.fs.ReadAt(...)`），答复是 head + 内容 + tail
- 属主侧的 `FS.Stat` **存在但不可达** —— 没有任何协议路径能调用它

所以"复核"要么**改协议**（加字段或加 `Kind`），要么**做不到**。评审子代理指出
这正是我一个**自相矛盾**的地方（§六 说不能加 stat，§九 说会向属主复核），
**它是对的**。冻结文档 §4.9 描述了一个未实现的协议要求 —— 这是**冻结文档自身的
一个缺口**，不是挂载层的缺口。

**决定：接受"元数据的新鲜度 = 索引的新鲜度"，不为此改协议。** 理由与边界：

1. **"树说谎"里最危险的那一半被内容路径挡住了。** 大小可能陈旧，但
   **`read` 永远从属主的真磁盘取内容**（`FS.ReadAt` → `os.Open`），所以
   **内容不会说谎**。挂在 `getattr` 上的 `Size` 会让内核**按索引大小截断**，
   而截断到一个**比真文件小**的前缀是**无害**的：读一个正在变大的文件，你会先读到
   旧的前缀，事件到达后就正确了。这不是损坏，是延迟。
2. **真正的危险是缩小的文件**（索引说 1 MiB，实际 4 KiB）。此时读超过 4 KiB 会得到
   `EIO`。**这不是静默损坏，是显式错误**，而且 D4/D5 把窗口限制在 1 秒 + 事件失效。
3. **我不认为这足以证明必须改协议。** 加 `KindStat` 会让每次 `getattr` 变成**两次**
   往返（`List` + `stat`），给一个 MVP 加一条协议路径，换掉一个**有上界且方向安全**
   的陈旧窗口。**如果实测证明这个窗口会咬人，正确的修法是加 `stat`** —— 那时它
   有证据支撑，而不是现在凭担心加。

**如实记录在这里，而不是藏起来**：这是**唯一一条我说"做不到"的冻结文档要求**。

### 明确需要动 `proto` 的两处（仅此两处）

1. **`EventBody` 加 `Seq uint64`**（D5）—— **加字段**，不改已有字段、不改 `Kind`
2. **错误 `Err` 文本加稳定 token**（D6）—— 改**字符串约定**，不改结构

这两处我都认为是**必要的**，而且都比"不改协议"这条原则更轻：它们是**增量**，
不破坏任何现有对端。

**另一个待定项：client 上下线要不要广播。** 现在 `Register`/`Unregister`
**不广播**，所以一台机器出现或消失只有重新 `List` 才看得到。
- **Linux**：FUSE 每次 `readdir` 都重新问，所以**基本够用**
- **Windows**：WinFsp 会缓存目录项，**需要显式通知**，否则根目录会一直显示一台
  已经离开的机器
- **决定：本计划不为它改 server。** Linux 上不需要；Windows 既然已按 D13 推迟，
  这个需求也一起推迟。**如果将来做 Windows，这是第一个要补的 server 改动。**

## 七、测试策略（最高风险项，所以最详细）

设计文档 §7 点名"**误删真文件**"是最严重的失败模式。挂载层能删、能改名，作用的
是**远端真磁盘**。所以测试策略比 v1 更重。

### 分层

1. **可移植核的单元测试**（无挂载、任何平台都跑）
   - 路径解析与规范化
   - 块缓冲的命中、淘汰、**两级上限**（单一 open 的上限，**以及全局上限真的把总量
     钉住** —— 开 N 个 open 断言总量不超过 `--buffer-total`）
   - `errnoFor` 的完整映射表（每个定点错误 + 每个 token）
   - **token 覆盖测试**：穷举性断言每个已知错误路径都带一个 token（漏掉的会退化成
     `EIO`，所以这条测试是防"我漏了一处"的唯一手段）
   - `rename` 何时返回 `EXDEV`
   - **D10 的强制回写表逐条**：`fsync`、脏 open 的 `rename`/`unlink`/`truncate`、
     卸载时有脏 open —— 每一条都断言"冲刷**发生**了"以及"**冲刷失败时目标未被修改**"
   - **D11 的重连状态机**（用假 viewer 注入断线）：重连后重新 `Watch`、重连期间
     报 `EIO`（**断言不是 `ENOENT`**）、超阈值后自卸载、断线时脏 open 被丢弃并记录
   - **D5 的丢更新探测**：序号跳变 → 触发"交出去的表"的作废
   - **D12 的符号链接拒绝**：`Mode` 带 `ModeSymlink` → `open` 返回 `ELOOP`
2. **FUSE 绑定测试**（有 FUSE 的机器）
   - 真实挂载到一个临时目录，用普通文件 API 操作，断言落到 fake/真 server
   - 覆盖：建、读、写、**`fsync`**、截断、改名、删、空目录、非空目录
   - `--exclude` 与落点检查
   - **编辑器模式**：`open(tmp)` → 写 → `rename(tmp, target)`（v1 版没测这个，
     而它正是设计文档 §4.5 点名的真实场景）
3. **端到端**（真 server + 真 client + 真挂载）
   - 设计文档 §1 那三句成功标准，逐句断言
   - **特别是第三句**：通过挂载点写入 → 去"供货方"的磁盘上断言字节真的变了
   - **真 server 重启**：挂载点自己恢复（D11），恢复后能读到变化
4. **安全测试**（这块单独列，因为它是"真丢文件"）
   - **D10 那张表的每一行**都要有"失败时目标未被修改"的断言
   - 拒绝路径：挂载点内、逃逸、跨机改名、符号链接
   - 一条 `rm` 的路径错误**绝不能**带走一整棵树

### 本机无法验证的部分，必须如实标注

- FUSE 需要内核支持与 `/dev/fuse`；本机是 Windows，**跑不了 Linux FUSE 集成测试**
- **但是 `GOOS=linux CGO_ENABLED=0 go build ./...` 在本机是通的**（实测），所以
  第 1 层测试**能在本机跑**，第 2、3 层不能
- WinFsp 需要安装第三方内核驱动，且绑定是 cgo 的（D13）—— 本机也不通
- 所以：**可移植核能在本机被完整测试，平台壳不行**。这一条要写进计划，
  不能假装集成测试跑过了。

## 八、CLI

```
usage: peerfold mount [--point PATH] [--buffer SIZE] [--buffer-total SIZE] [--allow-other]
```

- `--point`：挂载点，默认 `~/peerfold`（Linux）/ `%USERPROFILE%\peerfold`（Windows）
- `--buffer`：**单一 open** 的块缓冲上限，默认 64 MiB
- `--buffer-total`：**所有 open 合计**的上限，默认 256 MiB（D3 的两级上限）
- `--allow-other`：允许其他用户访问挂载点。**默认关**（FUSE 默认只对挂载者可见，
  这是个安全默认）

配置里加对应字段（`mount_point`、`buffer_limit`、`buffer_total`），与现有 `server`
字段同样处理。

## 十、留给实现者的（你们自己拿主意）

- **用哪个 FUSE 库**：`bazil.org/fuse`（单线程、API 简单、**无 tag 版**，要拉

  设计（D8），`hanwen` 的性能上限更高。**我倾向 `bazil`**，理由是它和 D8 的
  串行模型同构、调试面更小 —— 但这是实现者的判断，不是设计约束。
- 块缓冲的淘汰算法细节（LRU 还是别的；**跨 open 淘汰**时怎么选受害者）

- 事件到达时失效的**粒度**（整 inode？只失效目录？）

  攒出无限的表；超过上限时**如实记录"无法完整作废"**）
- **D6 的 token 名单**：具体用哪些 token、放在哪一层加（`internal/client` 还是
  `internal/server` 还是两边）—— 我倾向**在错误产生的地方加**（属主的
  `os` 错误在 client 侧映射成 token）
- 平台壳的具体接口选择与调用顺序

## 十二、成功标准（可判定的）

1. 在观察者上 `peerfold mount` 之后，`cd ~/peerfold && ls` 立刻列出所有 client
2. `cat ~/peerfold/win/Documents/notes.txt` 出内容
3. 用**普通编辑器**（或 `echo > file`）通过挂载点改一个文件并保存 → 去供货方的
   磁盘上断言字节真的变了
4. 供货方那边改一个文件 → 观察者这边**打开时看到新内容**（不是页缓存里的旧的）
5. 跨 client 的 `mv` 返回 `EXDEV`（`mv` 命令自己退化成复制+删除）
6. 非空目录 `rmdir` 被拒绝
7. 挂载点不在任何共享里时挂载成功；被包进共享时**拒绝挂载并说明原因**
8. **`fsync` 之后立刻杀掉属主进程**，重启后内容仍在（D10 的强制回写真的落盘了）
9. **server 重启**之后挂载点自己恢复，不需要用户重挂（D11）
10. 共享里的**符号链接**被拒绝（`ELOOP`），**不是**返回 9 字节的怪文件（D12）
11. **Linux 集成测试全绿**（第 2、3 层测试在有 FUSE 的机器上跑）

**v1 版这条原来写的是"两平台各自的集成测试在同一套可移植核上通过" —— 已删。**
按 D13，Windows 壳在本计划里**既不实现也不承诺**，所以不能出现在成功标准里。
一条无法验证的成功标准比没有更糟。

## 十三、这一层做完之后的诚实边界

做完本文（**Linux 侧**），**MVP 完成**：peerfold 是可以天天用的东西。但它仍然
**不是**：

- **跨平台**的 —— Windows 按 D13 是后续计划
- 可以扔到公网上的东西（无认证无加密）
- "什么都不用管"的常驻服务（没做开机自启）
- 快的（大文件首次打开慢；D4 的正超时意味着目录列举会明显慢）
- **对符号链接友好的** —— 它是**拒绝**而不是跟随（D12）

这五条都是**有意**的取舍，写在这里，而不是留在"以后再说"里。
